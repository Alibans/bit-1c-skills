# Тиражное расширение Первого БИТа

Расширения, которые продаются многим клиентам «как есть», должны выглядеть одинаково, кто бы из разработчиков их ни
писал: у пользователя — раздел «Первый БИТ» с понятной справкой, у сервиса 1С:Фреш — код, который проходит аудит,
у менеджера — описание и карточка для клиента. Этот скилл задаёт стандарт и даёт заготовку, из которой расширение
создаётся за минуту.

Стандарт написан для «1С:Бухгалтерии для Казахстана 3.0» (заготовка заимствует её язык и картинку раздела). Для
другой конфигурации создайте расширение скиллом `cfe-init`, а затем перенесите объекты заготовки и перезаимствуйте
картинку `Руководителю` (`cfe-borrow`).

## Как это выглядит у пользователя

```
Раздел «Первый БИТ» (картинка «Руководителю»)
├── <подразделы под задачу> — только те, что нужны этому расширению, например:
│     «Работа с документами» (обработки, команды), «Отчёты», «Настройки» (форма настроек)
├── О расширении           — всегда: «Возможности расширения», обзор со значками «?»
└── Личный кабинет         — всегда: сайт для заявок на линию консультаций
```
Обязательны только сам раздел, «О расширении» и «Личный кабинет». Остальные подразделы разработчик выбирает по
задаче: расширению, которое лишь добавляет колонку в типовой список, свои подразделы не нужны вовсе, а набору
отчётов достаточно «Отчёты». Пустой подраздел не создавать.
- На каждой своей форме — кнопка «?» (подробная справка по этой форме).
- Страница «Возможности расширения» — что добавлено и где; значок «?» у каждой возможности открывает её справку.
- Все страницы в одном оформлении (шрифт Segoe UI, синие заголовки #33499e, таблицы, плашки-примечания).

## Имена (проверяются скриптом заготовки)

| Что | Правило | Пример |
|---|---|---|
| Имя расширения | `БИТ_<Имя>`, CamelCase, без пробелов | `БИТ_КонтрольЦен` |
| Синоним | начинается с «БИТ: » | «БИТ: Контроль цен» |
| Поставщик / версия | «Первый БИТ» / `1.0.0.1`, каждая выдача клиенту — новая версия | `1.0.0.2` |
| Основная роль | `БИТ_ОсновнаяРоль<Имя без БИТ_>`, синоним «<синоним> — основная роль» | `БИТ_ОсновнаяРольКонтрольЦен` |
| Свои объекты | `<Имя расширения>_<Что>` | `БИТ_КонтрольЦен_Обработка`, `БИТ_КонтрольЦен_Справка` |
| Свои реквизиты в заимствованных объектах | тоже с префиксом расширения | `БИТ_КонтрольЦен_ДатаПроверки` |
| Раздел | имя `<Имя>_ПервыйБИТ`, синоним всегда «Первый БИТ» | `БИТ_КонтрольЦен_ПервыйБИТ` |

**Почему префикс у всех своих объектов.** Платформа не даёт двум расширениям в одной базе иметь объекты с одинаковым
именем — второе просто не применится («Уже существует объект с именем …»), а заимствовать объект из другого
расширения нельзя. Клиент может купить несколько наших решений, поэтому каждое расширение называет свои объекты своим
префиксом. Цена решения: у клиента с двумя расширениями будет два раздела «Первый БИТ» — каждый со своими командами.

**Имя роли и объектов не меняется между версиями.** При обновлении объект с другим именем — это новый объект:
пользователи потеряют роль, настройки и данные реквизитов.

**Префикс — `БИТ_` кириллицей** (старые расширения с `BIT_` не переименовывать без просьбы). Префиксы по имени
клиента (`<Клиент>_…`) не использовать. Перед загрузкой в базу сверить, что имена ролей и
общих модулей не пересекаются с другими расширениями этой базы. Отдельные (выделенные из монолита) расширения не
ставятся в одну базу друг с другом и с монолитом — одинаковые имена и uuid; «два инструмента одному клиенту» = один
манифест сборки.

**Конфиденциально:** код лицензирования БИТ, пароли модулей, адрес и пароль публикации менеджера лицензий — не
цитировать, не сохранять в файлы и память, не публиковать (в том числе в открытое зеркало скиллов).

**Тексты справок и описаний пишет Claude** и сначала показывает пользователю на одобрение. Аудитория — бухгалтеры: без
механики лицензии, без отсылок «обратитесь в поддержку», единый стиль справки во всех расширениях.

## Порядок работы

### 1. Создать исходники из заготовки
```
powershell.exe -NoProfile -ExecutionPolicy Bypass -File <скилл>\scripts\new-extension.ps1 `
    -Name БИТ_КонтрольЦен -Synonym "БИТ: Контроль цен" -OutDir <проект>\src\БИТ_КонтрольЦен `
    -Sections "Работа с документами,Настройки"
```
`-Sections` — подразделы под задачу в порядке показа (можно не указывать); имя подсистемы скрипт строит из
названия («Работа с документами» → `РаботаСДокументами`). Скрипт копирует `assets/skeleton`, подставляет имя,
синоним, роль и версию и выдаёт новые идентификаторы всем объектам (ссылки на типовую конфигурацию и классы
платформы сохраняет). Готово: раздел «Первый БИТ» с «О расширении» и заказанными подразделами, команды
«Личный кабинет» и «Возможности расширения», форма справки `<Имя>_Справка`, страница `<Имя>_ОписаниеВозможностей`,
основная роль в «ролях по умолчанию». Заготовка проверена: созданные из неё расширения (с подразделами и без)
загружаются в одну базу вместе и проходят проверку применимости и модулей.
Подраздел, понадобившийся позже, добавляется скиллом `subsystem-edit` / `subsystem-compile` внутрь `<Имя>_ПервыйБИТ`.

### 2. Добавить функциональность
- Заимствование типовых объектов — `cfe-borrow`, перехваты методов — `cfe-patch-method`, свои объекты —
  `meta-compile`, формы — `form-add` / `form-edit`, макеты — `template-add` / `mxl-compile`. Перед кодом — `1c-standards`.
- Код сразу под Фреш: прочитать `references/fresh.md` **до** написания кода (длительные операции, настройки без
  констант, асинхронные диалоги, РАЗРЕШЕННЫЕ, не ломать типовые формы, свои макеты вместо заимствованных типовых).
- Свои команды, обработки и отчёты включить в подходящий подраздел
  (`Subsystems/<Имя>_ПервыйБИТ/Subsystems/<Подраздел>.xml`, элемент `Content`) — скилл `subsystem-edit`;
  форму настроек — в «Настройки». Если расширение только дорабатывает типовые формы (колонка, поле, печать),
  своих подразделов может не быть: пользователь узнаёт о доработке из «Возможностей расширения».

### 3. Справка (обязательно для каждой своей формы и каждой возможности)
Справку пишут для бухгалтера, а не для разработчика: назначение, что заполнить заранее, шаги, что получится,
что делать, если не получилось. Кнопки и поля — так, как они называются на экране.

1. **Страница справки** — общий макет `<Имя>_Справка_<Раздел>` (тип «Текстовый документ», текст — HTML из
   `assets/help/справка-шаблон.html`). Проще всего скопировать пару файлов макета
   `CommonTemplates/<Имя>_ОписаниеВозможностей(.xml)` под новым именем, поменять имя/синоним/uuid и добавить
   `<CommonTemplate>` в `Configuration.xml`.
2. **Регистрация** — строка в `ОписаниеРаздела()` модуля формы `<Имя>_Справка`:
   `Разделы.Вставить("prices", Новый Структура("Макет, Заголовок", "<Имя>_Справка_КонтрольЦен", НСтр("ru = 'БИТ: Контроль цен'")));`
3. **Кнопка «?»** на форме — команда формы `БИТ_Справка` (заголовок «?», подсказка «Справка») в командной панели:
   ```bsl
   &НаКлиенте
   Процедура БИТ_Справка(Команда)
   	ОткрытьФорму("ОбщаяФорма.БИТ_КонтрольЦен_Справка", Новый Структура("Раздел", "prices"));
   КонецПроцедуры
   ```
4. **Справка формы платформы** (F1) — тот же текст в `Ext/Help/ru.html` своей формы/обработки/отчёта.
5. **«Возможности расширения»** — заполнить `CommonTemplates/<Имя>_ОписаниеВозможностей/Ext/Template.txt`
   (в заготовке — шаблон с подсказками ЗАГЛАВНЫМИ буквами, их не оставлять): по строке на возможность, значок
   `<a class="help" href="bithelp:<ключ>">?</a>` ведёт на её страницу справки.

### 4. Проверить и собрать .cfe
1. `cfe-validate` по каталогу исходников — 0 ошибок.
2. Загрузить в **тестовую** базу (копию, не рабочую), где нет других расширений с теми же объектами:
   `db-load-xml -Mode Full -Extension <Имя> -UpdateDB`. Пакетный Конфигуратор не понимает кириллицу в пути —
   исходники и выгружаемый .cfe держать во временной папке с коротким ASCII-путём, потом копировать.
3. `db-cfe-admin -Command check -Checks apply,modules -Context ThinClient,Server,WebClient` — всё «ОК».
4. Открыть в тонком и веб-клиенте под пользователем без прав администратора: раздел «Первый БИТ», «?», основные
   сценарии. Если не проверяли — честно написать об этом.
5. Выгрузить `.cfe` (`db-dump-cf -Extension <Имя>`) → `releases\<Имя> v <версия>.cfe`. Старые версии не хранить.
6. Пройти чек-лист `references/fresh.md` и оформить таблицу «требование → как выполнено / что не проверено».

### 5. Документы для продажи (обязательны для каждого расширения)
Прочитать `references/documents.md` — там правила и образцы. Комплект в папке расширения:

1. **Внутреннее описание по шаблону БИТ** — `БИТ <Название> - описание решения (внутреннее).docx`, ровно 16
   разделов. Текст разделов — в `description.json` (образец `assets/docgen/description-example.json`), документ
   собирает `node assets\docgen\make-description.js description.json <вывод>.docx` в оформлении шаблона, со
   скриншотами.
2. **Ограничения — прямо и конкретно** (раздел 10): где именно работает («только документ …», «только печатная
   форма …»), что в другой функциональности — «только отдельной доработкой», как ведёт себя в пограничных случаях,
   что заменяет в типовой, с чем не совместимо, что нужно заранее. Менеджер продаёт по этому тексту — клиент не
   должен потом обнаружить, что «у него не так».
3. **Клиентская PDF-карточка** — `БИТ <Название> - карточка решения для клиента.pdf` (+ .docx): одна страница на
   фирменном бланке, текст в `card.js` (образец `assets/docgen/card-example.js`), сборка
   `assets\docgen\make-card.ps1 -Card card.js -Out <вывод>`. **Только цена в тенге, без часов.** Если ограничение
   влияет на решение клиента — блок «Важно знать» (1–3 пункта языком клиента).
4. **Краткое описание** в 2–3 предложения с условным примером значения («если указать 5 — …, если 10 — …»).
5. `.cfe` текущей версии.

Скриншоты для описания и карточки — живые, из **демобазы** (не из базы клиента): порядок и инструменты —
`references/screenshots.md` (данные готовятся кодом через Toolkit, формы открываются открывалкой, окно 1С снимается
скриптом, в т.ч. в уже открытом сеансе, если лицензия пускает одного клиента).

`description.json`, `card.js` и картинки хранить в проекте рядом с исходниками — при новой версии документы
пересобираются, а не пишутся заново.

## Кодировки и мелочи
- Все XML, BSL, HTML-макеты и `.ps1` с кириллицей — UTF-8 **с BOM** (часть инструментов пишет без BOM — проверять
  первые байты EF BB BF). Переводы строк не менять (в выгрузке 1С — CRLF).
- Не править сгенерированные выгрузки руками «на глаз»: после правок — снова `cfe-validate`.
- Команда «Личный кабинет» ведёт на `https://lk.1cbit.kz` — данные не передаёт; не удалять, это единый стандарт.

## Что нужно на компьютере разработчика
- Платформа 1С 8.3.21+ и тестовая (файловая) копия базы клиента без наших расширений.
- Скиллы работы с 1С: `cfe-init`, `cfe-borrow`, `cfe-patch-method`, `cfe-validate`, `meta-compile`, `form-edit`,
  `subsystem-edit`, `db-load-xml`, `db-cfe-admin`, `db-dump-cf`, `1c-standards` (желательно `1c-fresh`).
- Для документов: node, 7-Zip (`C:\Program Files\7-Zip`), Microsoft Word.
- Установка скилла: скопировать папку `1c-bit-extension` в `%USERPROFILE%\.claude\skills\`.
