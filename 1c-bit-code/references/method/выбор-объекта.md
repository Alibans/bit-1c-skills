# Какой объект метаданных создать и как его описать

Стандарты: std603, std432, std728, std704, std697, std474, std550, std478, std531, std649.

## Какой вид объекта
Сначала понять, что меняется и кто это меняет:
- **Событие, которое произошло в какой-то момент** — это документ. Учётные данные из него попадают в регистры при проведении. Документ, который не проводится, считается черновиком (std603).
- **Относительно постоянный список, который ведёт пользователь** — справочник.
- **Набор значений, известный при разработке** — перечисление. Чтобы добавить значение, нужно менять конфигурацию, пользователь этого сделать не может.
- **Набор видов, который пользователь сам будет дополнять** — план видов характеристик. Если в требованиях звучит «потом добавят свои виды», перечисление не подходит.
- **Одно значение на всю базу** — константа.
- **Количество или сумма, которая накапливается, или состояние по ключу** — регистр (см. [регистры.md](регистры.md)).

## Реквизиты
- **Строка** — переменной длины, и максимум задан всегда (std432). Если длину определяет внешний документ (ИИН/БИН, номер счёта), берём её. Неограниченная длина допустима в двух случаях: комментарий в многострочном поле и служебные тексты, которые пишет программа.
- **Составной тип** (std728): если по реквизиту соединяют, отбирают или сортируют, в нём должны быть только ссылочные типы. Строку, число и дату туда не смешивать: такие запросы заметно медленнее. Тип `ЛюбаяСсылка` и общие `СправочникСсылка`/`ДокументСсылка` не использовать, типы перечислять явно. Для маленьких таблиц (до ~1000 записей) допустимо исключение.
- **Определяемый тип** (std704) нужен, если один тип используется во многих местах и при внедрении может измениться. Для одного-двух реквизитов он не нужен.
- **Проверка заполнения** — «Выдавать ошибку», если реквизит обязателен хотя бы в одном сценарии. Условные случаи решаются в `ОбработкаПроверкиЗаполнения` (см. [события-объекта.md](события-объекта.md)).
- Заполнять **значение заполнения**, если значение по умолчанию известно. Заполнять **связи и параметры выбора**, если допустимые значения зависят от других реквизитов или условия отбора известны заранее.
- Если документ создаётся на основании другого, заполнять все реквизиты, которые наследуются (std649).

## Имена и представления (std474, std550)
- Документ называем в единственном числе и по сути процесса, а не по печатной форме: `СверкаВзаиморасчетов`, а не `АктСверки`. Слова, без которых смысл не меняется («Документ…»), не пишем.
- Синоним — без сокращений, кроме общепринятых (НДС, ИИН). Правило касается и реквизитов, табличных частей, измерений и ресурсов.
- Представление объекта — в единственном числе, представление списка — во множественном. Если оно совпадает с синонимом, не задаём. В командном интерфейсе текст не длиннее 38 символов, лучше до 30.
- У документов есть реквизит «Комментарий» (std531).
- Если код справочника не несёт смысла, ставим длину кода 0.

## Предопределённые элементы (std697)
- Режим обновления предопределённых оставляем `Авто` и из кода его не переключаем.
- Права на интерактивное удаление и пометку удаления предопределённых не выдаём.
- В РИБ подчинённые узлы получают предопределённые элементы только из главного узла. Код, который их создаёт или заполняет, запускаем только в главном узле.

## Стоп
- Изменить тип, длину или состав составного типа у реквизита, где уже есть данные, — только вместе с планом переноса этих данных.
