# Проверка своего кода перед сдачей

Проверяется **только то, что написано или изменено в этой задаче**. Типовой код, заимствованные фрагменты и
старый код вокруг замечаниями не считаются, даже если они не по стандартам.

## 1. Определить, что своё

**Проект в git.** Своё — изменения от точки, где задача началась:
- назван коммит — `git diff X~1 X`; диапазон коммитов — `git diff A~1 B`; ветка — `git diff <ветка>...HEAD`;
- к этому всегда добавить незакоммиченное: `git diff HEAD` и новые файлы из `git status --porcelain`;
- ничего не названо и незакоммиченного нет — спросить, с какого коммита считать.

**Нет git — по виду работы:**
- **расширение (исходники XML)** — объекты, которые не заимствованы (в XML объекта нет
  `<ObjectBelonging>Adopted</ObjectBelonging>`), и в модулях заимствованных объектов — свои методы и обёртки
  `&Перед`/`&После`/`&Вместо`, свои элементы и реквизиты в заимствованных формах;
- **внешняя обработка или отчёт** — весь код свой;
- **доработка прямо в конфигурации** — по меткам или сравнением с типовой той же версии; нет ни того, ни другого —
  спросить, какие модули и методы свои.

**Внутри diff тоже действует правило заимствования:** в `&ИзменениеИКонтроль` своё — только содержимое
`#Вставка … #КонецВставки` и сам факт `#Удаление`; скопированный из типовой код, даже новый в diff, не проверять.

**Не код — не проверять:** служебные файлы выгрузки (`ConfigDumpInfo.xml`), бинарные сборки (`.cfe`, `.epf`, `.erf`),
тестовые и разовые скрипты, их выводы, документы. `Package.bin` XDTO, `Form.xml`, XML объектов — проверять только
на то, что относится к правилам (ссылки на свои реквизиты, имена, права).

Чтобы понять правку, метод можно читать целиком, но замечания — только к изменённым строкам.

В начале отчёта написать, что проверено и что пропущено: «git diff f604b31: 5 файлов, ~100 строк; пропущены
тесты и ConfigDumpInfo.xml».

## 2. Пройти по своему коду

Смотреть только разделы, которые касаются изменений:

| Что изменено | Что проверять |
|---|---|
| Любой BSL | SKILL.md: «Просто», «Устройство модуля», «Ошибки», «Комментарии и имена»; [частые-ошибки.md](частые-ошибки.md); быстрый поиск Фреша (ниже) |
| Запросы | SKILL.md «Данные из базы»; [стандарты.md](стандарты.md) «Запросы»; `РАЗРЕШЕННЫЕ` |
| Запись, проведение, транзакции | [стандарты.md](стандарты.md) «События объекта», «Конструкции языка»; [method/](method/README.md) по теме |
| Формы (BSL и `Form.xml`) | [стандарты.md](стандарты.md) «Клиент-сервер и формы»; [fresh.md](fresh.md) разделы 2, 5 |
| HTTP-сервис, обмен, загрузка | SKILL.md правила 16–20; [method/загрузки-и-фоновые.md](method/загрузки-и-фоновые.md); [fresh.md](fresh.md) раздел 7 |
| Метаданные, роли | [стандарты.md](стандарты.md) «Метаданные» |
| Доп. обработка или отчёт | [стандарты.md](стандарты.md) последний раздел; [fresh.md](fresh.md) вступление |

Быстрый поиск Фреша по своим строкам: `Выполнить(`, `Вычислить(`, `COMОбъект`, `ПодключитьВнешнююКомпоненту`,
`УстановитьПривилегированныйРежим`, `HTTPСоединение`, `Новый Файл`, `ЗаписьТекста`, `Вопрос(`, `Предупреждение(`,
`ОткрытьФормуМодально`, `ВвестиЗначение(`, `Сообщить(`; запросы без `РАЗРЕШЕННЫЕ`.

Проверка платформой (`/CheckConfig -ThinClient -WebClient -Server`, для расширения `-Extension <Имя>`; загрузка в
базу) — только в своей тестовой базе или с разрешения пользователя. Нет такой — записать в «Не проверено».

## 3. Не усложнять проверкой

- Замечание — только про реальную проблему: ошибка, риск для данных, не пройдёт Фреш, явное нарушение правила.
  Вкусовщину и «можно было бы красивее» не писать.
- Исправление — минимальное, в одну строку. Не предлагать новые механизмы, слои, общие модули и настройки, если
  проблема решается без них.
- Переусложнение — тоже замечание: механизм без причины, дубль, мёртвый код, функция «на будущее», лишний параметр.
- Найденное без просьбы не исправлять — сначала показать таблицу.

## 4. Итог пользователю

| № | Файл:строка | Что не так | Важность | Как исправить |
|---|---|---|---|---|

Важность — по последствиям, а не по тому, есть ли номер правила:
- **высокая** — ошибка в данных, не будет работать, не пройдёт Фреш, дыра в правах;
- **средняя** — сработает, но есть риск: потеря причины ошибки, гонка, медленно на большой базе, заметная лишняя сложность;
- **мелочь** — оформление, мелкий дубль, неточный текст.

Чек-лист целиком не выводить: после таблицы одна-две строки «по остальным пунктам замечаний нет», с перечнем того,
что смотрел.

Ниже — отдельно:
- **Вне задачи** — явные ошибки, замеченные рядом в коде, который в эту задачу не менялся (типовом, заимствованном
  или своём старом), коротко и без исправлений. Нет таких — не писать раздел.
- **Не проверено** — что не запускалось: проверка платформой, пользователь без полных прав, веб-клиент,
  клиент-серверная база, аудит сервиса, ответ внешней системы.
